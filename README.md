## 기능 요구사항

- 로또 구입 금액을 입력하면 구입 금액에 해당하는 로또를 발급해야 한다.
- 로또 1장의 가격은 1000원이다.
- 로또 당첨 번호를 받아 일치한 번호 수에 따라 당첨 결과를 보여준다.
- 2등을 위한 보너스볼을 추첨한다.
- 당첨 통계에 2등을 추가한다.
- 2등 당첨 조건은 당첨 번호 5개 일치 + 보너스 볼 일치다.
- 현재 로또 생성기는 자동 생성 기능만 제공한다. 사용자가 수동으로 추첨 번호를 입력할 수 있도록 해야 한다.
- 입력한 금액, 자동 생성 숫자, 수동 생성 번호를 입력하도록 해야 한다.

## 필요한 도메인 객체

### lotto

- `LottoNumber`: 로또 번호 (1~45 범위의 원시값 포장)
- `LottoNumbers`: 로또 번호 6개를 담는 일급 컬렉션
- `Lotto`: 로또 한 장 (LottoNumbers를 포함)
- `Lottos`: 구매한 로또들을 담는 일급 컬렉션
- `LottoNumberGenerator`: 랜덤 로또 번호 생성기
- `WinningLotto`: 당첨 번호와 보너스 번호를 가진 객체
- `Rank`: 당첨 등수를 나타내는 Enum (1등~5등, 낙첨)
- `LottoResult`: 당첨 결과 통계를 담는 객체

### purchase

- `Money`: 금액을 나타내는 원시값 포장 객체
- `LottoFactory`: 수동/자동 로또 생성 팩토리
- `PurchaseCalculator`: 구매 금액으로 로또 개수 계산

## 고민한 점

### 일급 컬렉션 설계

- `LottoNumbers`는 `List<LottoNumber>`를 감싸는 일급 컬렉션으로 설계하였으며, 로또 번호가 **항상 6개이고 중복되지 않으며 정렬된 상태**임을
  보장하도록 구현하였습니다.
- `Lottos`는 `List<Lotto>`를 감싸는 일급 컬렉션으로, 사용자가 구매한 로또 목록을 하나의 도메인 개념으로 표현하고 불변으로 관리하도록 설계하였습니다.
- 컬렉션을 그대로 노출하기보다는 일급 컬렉션을 사용함으로써, **컬렉션에 대한 검증 로직과 비즈니스 로직을 한 곳에서 관리할 수 있도록 하는 점을 중점적으로 고민하였습니다.**

### 로또 도메인 객체 구조화

- 로또 도메인을 `LottoNumber` → `LottoNumbers` → `Lotto` → `Lottos`의 계층 구조로 나누어 설계하였습니다.
- 각 객체가 자신의 상태를 스스로 검증하도록 책임을 명확히 하고, 상위 객체가 하위 객체의 내부 구현에 의존하지 않도록 설계하고자 하였습니다.
- 모든 도메인 객체는 불변 객체로 구현하여, 생성 이후 상태 변경으로 인한 부작용을 최소화하려고 하였습니다.
- 당첨 등수와 상금 정보는 `Rank` enum을 통해 하나의 타입으로 관리함으로써, **등수에 대한 규칙과 데이터를 분산시키지 않도록 고민하였습니다.**

### 책임 분배

- 도메인 객체는 자신의 상태를 검증하고, 해당 도메인과 관련된 비즈니스 로직만 수행하도록 책임을 제한하였습니다.
- `WinningLotto`는 로또 번호 비교를 통해 당첨 여부를 판단하고, 그 결과로 `Rank`를 반환하는 책임을 가지도록 설계하였습니다.
- `LottoFactory`는 수동/자동 로또 생성에 대한 책임을 가지며, 생성 방식이 변경되더라도 다른 도메인 객체에 영향을 주지 않도록 역할을 분리하였습니다.
- `LottoVendingMachine`은 전체 흐름을 제어하는 역할만 담당하고, 실제 비즈니스 로직은 도메인 객체에 위임하도록 설계하였습니다.
- View는 입출력만을 담당하도록 분리하여, 도메인 로직이나 내부 구현에 대해 알지 못하도록 구성하였습니다.

## 리뷰 피드백 정리

### 커스텀 예외 관리

예외를 전부 커스텀해서 관리했을 때의 장점으로는 각 상황에 맞는 구체적인 예외를 나타낼 수 있다고 생각합니다.
단점으로는 말씀하신 대로 비즈니스 요구사항이 커지게 되면 수많은 구체적인 예외사항이 발생하는데, 이때마다 하나씩 클래스를 추가하여 커스텀 예외를 만드는 비용이 기하급수적으로 늘어날
것 같습니다.

개선할 방법으로는 도메인별로 LottoException, PurchaseException등으로 러프하게 나눈 후 그 안의 구체적인 에러 메시지를 같이 전달하여 관리하는 방법이 있을
것 같습니다!

### 정적 팩토리 메서드

LottoNumbers 에서 사용한 정적 팩토리 메서드는 사용자의 입력을 파싱하는 로직을 두어 로또 번호의 생성 규칙을 하나로 고정하기 위해 사용하였습니다.

### Collections.unmodifiableList() 의 불변성

찾아보니 Collections.unmodifiableList는 읽기 전용 뷰라서, 항상 불변을 보장하지 않습니다.
그 예시로는 this.lottos가 참조하는 리스트의 원본이 바뀌는 경우가 있습니다.

불변을 유지하기 위해선 Lottos의 생성자에서 List.copyOf()를 통해 불변 리스트를 가지고 있게 하는 방법이 있다고 생각합니다.

Collections.unmodifiableList()의 경우 읽기 전용 (UnmodifiableList) 뷰 객체를 반환하므로 복사가 일어나지 않습니다. 

방어적 복사를 사용하는 상황과 불변 컬렉션을 반환하는 상황에 대하여 생각해보았습니다.
이 상황의 경우 Lottos는 생성자에서 List<Lotto>를 받아 외부에서 사용하면서 변경될 가능성이 있으므로
복사 비용이 들더라도 불변성을 유지하는 것이 맞다고 생각합니다. 

방어적 복사만 허용하는 경우, 외부에서 주입 받아 관리하지 않고 내부에서 직접 만든 리스트를 관리하는 상황에서 사용할 수 있다고 생각합니다.


### LottoNumberGenerator 의 상태성

랜덤으로 생성하게 될 로또 번호들을 매번 생성하지 않고 재사용하기 위해, 상태를 가지게 설계하였습니다.
하지만 Collections.shuffle()로 매번 내부 상태가 변경되기 때문에, 매번 복사를 통해 내부 로또 번호의 불변성을 유지하도록 수정하겠습니다.

현재 코드에서는 한 번만 생성해서 생성자 호출이 한 번이라서 계속 생성되지 않는다고 생각했습니다.
하지만 클래스 자체가 한 번만 생성된다는 것을 보장하지 않기 때문에, 타입 수준에서 이걸 보장하기 위해서는
static pool을 사용하여 클래스 로딩 시점에 한 번만 생성할 수 있게 하는 게 더 나은 방법 같다고 생각합니다.
또한 1~45라는 로또번호의 범위는 고정 범위이기 때문에 static으로 관리하는 것이 좋은 것 같습니다.


### 상태가 존재하지 않는 객체

저는 상태를 가지지 않은 객체여도 도메인 개념을 표현한다면 객체가 될 수 있다고 생각합니다! 다만 PurchaseCalculator는 단순 계산의 행위만
한다고 생각하여, 인스턴스로 만들어 사용하지 않고 static 메소드로 수정하겠습니다.

### 로또의 가격을 알고 있는 객체: Lotto vs PurchaseCalculator

로또의 가격은 구매 정책에 포함되기보다는 고정된 하나의 속성이라고 생각되어, Lotto가 알고 있는 것이 적절하다고 생각합니다.
PurchaseCalculator는 단순 계산 행위만 하는 객체로 사용하는 것이 좋은 것 같습니다.

### LottoFactory 도입 이유

로또 수동/자동 구매 로직이 여러 곳에 흩어지면 생성 방식 변경 시 수정 범위가 커질 수 있어서, 생성 책임을 LottoFactory로 모았습니다. 또한 자동 로또는
LottoNumberGenerator를 주입받아 생성하도록 분리해서 테스트에서 고정된 생성기를 넣기 쉽고, 생성 전략 변경도 팩토리 내부에서만 처리되도록 했습니다. 
흐름 제어 클래스는 생성 세부 구현을 몰라도 되도록 하여 책임을 분리하려는 의도였습니다.

### Lotto 클래스의 의미

현재 Lotto 클래스는 자신의 Price를 알고, LottoNumber를 포워딩하는 역할을 하고 있습니다.
단순히 현재 상태만 보면 LottoNumber만 가지고도 충분히 Lotto의 역할을 대신할 수 있을 것 같습니다.

하지만 추후 로또의 발급 시각 등을 나타내고 싶을 때는 Lotto 클래스에 해당 필드를 관리할 수 있게 하면 좋을 것 같습니다.
